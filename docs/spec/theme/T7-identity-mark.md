# T7 — Identity mark

Location: `src/features/theme/mark/`.

The circular glyph that appears in the navbar, footer, window picker, toasts, and the theme
picker. Renamed from "favicon" — that word is reserved for the browser tab icon, which is a
static PNG generated at build time from `tools/build-browser-icons.ts` and is
a different thing entirely. Conflating them is why `getOptimizedThemeConfigForFaviconOnly`
exists and returns, in its own words, a type that "is very confusing and doesn't make sense at
all" (`lib/themeMaker/faviconHelper.tsx:52-54`).

## 1. Schema

```ts
export type MarkSource = {
  readonly mode: MarkMode;
  /** Stroke color. Defaults to the `brand` role. */
  readonly stroke?: ColorRef;
  /** Fill gradients. One entry ⇒ all regions share it; three ⇒ one per region. */
  readonly gradients?: readonly [MarkGradient] | readonly [MarkGradient, MarkGradient, MarkGradient];
  /** Only for mode "backdrop". Defaults to the theme's `page` surface. */
  readonly backdrop?: readonly GradientLayer[];
  /** Only for mode "scene". */
  readonly sceneId?: SceneId;
};

export type MarkMode =
  | "outline"    // stroke only
  | "unified"    // one gradient across the whole disc
  | "split"      // three regions, three gradients (the site's signature form)
  | "backdrop"   // the disc is a window onto a gradient stack
  | "scene";     // the disc hosts a backdrop scene (gallery, gallery3D today)

export type MarkGradient = {
  readonly angle?: number;                       // deg, default 0
  readonly stops: readonly MarkStop[];
};
export type MarkStop = { readonly offset: number; readonly color: ColorRef };
```

Changes from `FaviconConfig`:

| Before | After | Why |
| --- | --- | --- |
| `mode: "separate"` | `mode: "split"` | "separate" described the implementation, not the appearance |
| `mode: "overall"` | `mode: "unified"` | same |
| `mode: "custom"` + `customKey` | `mode: "scene"` + `sceneId` | the two "custom" marks are `gallery` and `gallery3D` — both are backdrop scenes rendered in a circular clip. One registry, not two. |
| `outline?: AccentColors \| HexColor` | `stroke?: ColorRef` | the union of "a role name or a hex string" is `ColorRef` (T3 §4); the `"site"` special case dissolves with F-07 |
| `backdropGradient?: ColorGradient[]` | `backdrop?: GradientLayer[]` | typed union |
| `backdropProhibitSVG?: boolean` | *(removed)* | see §3 |
| `FaviconGradientStop.color: HexColor` | `MarkStop.color: ColorRef` | a mark stop can now reference a tone, so the mark follows the seed |

That last row is the substantive one. Today every mark gradient is authored as verbatim hex,
so changing a theme's hue leaves its mark behind. With `ColorRef`, `velvet`'s mark is
`tone(0.70) → tone(0.45)` and recolors with the theme.

### 1.1 `mode: "scene"` renders live exactly once

The mark appears in the navbar, the footer, notification cards, the window picker, the theme
picker, and the design page's gallery — potentially a dozen instances on one route. Under
`mode: "scene"` with `sceneId: "gallery-3d"` that would be a dozen WebGL contexts, which is what
`Gallery3DFavicon` does today and is why the `gallery3D` theme is the heaviest in the set.

Rule: **at most one live scene mark per page.** `MarkHost` (a tiny module-level registry, not a
context) grants the live slot to the first mark that requests it with `priority: "primary"` —
in practice the navbar. Every other instance renders a **poster**: a static image generated at
build time by rendering the scene's first frame offscreen, stored under
`public/mark-poster/<themeId>.webp`. Posters are generated by `tools/build-mark-posters.ts`
alongside `themes.generated.css`.

The visible consequence is that the navbar mark animates and the footer mark does not, which is
correct — the footer mark is 32 px and its animation was never legible.

## 2. Rendering

`mark/Mark.tsx`, a **server component by default**. It takes `ResolvedMark` and emits SVG.
Nothing about it is interactive.

The current `ConfigFavicon` is a client component (`"use client"`) that calls `useTheme()`,
recomputes `hashAndEncode(themeConfig)` for gradient ids, and is the only `React.memo` in the
codebase — memoized precisely because it was expensive and re-rendered constantly. Under v11 it
reads its colors from CSS custom properties, so:

- **The mark is a server component** and appears in the initial HTML.
- **Gradient element ids are stable and content-independent.** The current
  `hashAndEncode(adaptedThemeConfig)` recomputes a SHA-256 of the entire theme object on every
  render to produce unique `<linearGradient id>` values. Replace with `React.useId()` for
  client instances and a deterministic counter for server ones. `crypto.createHash` per render
  is removed.
- **`memo` is unnecessary**, because there is nothing to re-render.

SVG stops reference custom properties:
```tsx
<stop offset={s.offset} stopColor={`var(--zw-mark-${region}-${i})`} />
```
compiled by T4 alongside the rest of the theme. So the mark recolors with the theme with no
React involvement at all — the same property as everything else in v11.

The `"backdrop"` mode's SVG-vs-CSS decision (`canUseTranslatedBackdropFavicon`, which inspects
every layer to decide whether it can be expressed as SVG gradients, and the
`backdropProhibitSVG` manual override) is replaced by:

- **Always** render `"backdrop"` mode as a `<div>` with the surface's `background-image` and a
  `border-radius: 50%` clip, using the same `--zw-surface-page-image` the page already uses.
  One code path.
- The SVG translation existed so that the mark could be exported as a standalone SVG file. That
  need is real but narrow (profile sharing, the design page's gallery), so it moves to an
  explicit `exportMarkSvg(resolved)` used by the export button — where a fallback rasterization
  is acceptable — rather than governing the runtime render path.

This removes `generateTranslatedBackdropGradients` (190 lines of gradient-to-SVG-transform
maths, including a bespoke `radial-gradient` size-keyword-to-matrix conversion) from the
runtime.

## 3. The prebuild pipeline

`prebuild-helper/prebuild.js` runs three scripts. All three are accounted for here:

| Script | Disposition |
| --- | --- |
| `website-favicon-generator.js` | → `tools/build-browser-icons.ts` (below) |
| `image-optimizer.js` | → `tools/optimize-assets.ts`. **Keep.** It runs `svgo` over `public/**` and strips leftover `vectornator:` attributes from Linearity-exported SVGs, which is real and still needed for the backdrop assets T6 §3.1 inlines. Two fixes: it silently swallows failures behind `doLog = false`, and its `EXCLUDED_PATHS` list is five hardcoded paths with no comment explaining why each is excluded — document them or delete the exclusions. `svgo` stays in devDependencies. |
| `svg-id-randomizer.js` | **Delete** (F-69). See below. |

`prebuild` is added to `package.json` so all of this runs on `build`, not only on `predev`
(it currently runs on neither — there is no `prebuild` script at all).

### 3.1 Replacing the id randomizer

F-69: the script rewrites `.tsx` files **in place**, prepending the sentinel `"id random";`. It
has already run over **19 files** under `components/assets/` — not two. `X2 FN-12` is sized for
that.

The replacement is not a blanket `useId`: `useId` requires a client component, and P1 §2 moves
~130 icons *to* the server. Per file:

1. **If the SVG has no internal references** (no `url(#…)`, no `xlinkHref`), the ids are inert —
   delete them and the sentinel. Expect this to cover most of the 19.
2. **If it has references but renders once per page** (the mark, the favicon backdrop), scope them
   with a deterministic prefix derived from the component name. No hook, no client boundary.
3. **Only if it can render more than once with different content** does it need `useId` and a
   client boundary. Expect one or two.

Each file's disposition is recorded in the task's PR, because "19 files, mechanical" and "19 files,
each a judgment call" are different jobs and the second one is what this is.

### 3.2 Browser icon

`prebuild-helper/website-favicon-generator.js` rasterizes three environment-specific SVGs to five
PNG sizes. It stays, moved to `tools/build-browser-icons.ts`, with two fixes:

- It currently runs only on `predev`, never on `build` (`package.json` has no `prebuild`
  script). Add `prebuild`.
- It calls `sharp(...).toFile(..., callback)` in a loop without awaiting, so the process can
  exit mid-write. Await them.

`<meta name="theme-color">` is set from the `brand` role. Today `ThemeApplier` sets it in an
effect that queries and mutates `document.head` (`ThemeApplier.tsx:28-37`). In v11 it is
rendered by the root layout from the server-known theme, and updated by `ThemeHost` only when a
runtime theme is active.

CSS-animated authored SVG motif, static palette-inheriting secondary SVGs, deterministic SVG/WebP
posters for external use, and browser SVG/PNG exports for full CSS backdrop stacks.
