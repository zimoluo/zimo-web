## 2. Color and theme engine

### F-01 · The shade map is not perceptual — `lib/themeMaker/colorHelper.ts:28-73`
`generateShadeMap` ramps HSL lightness `94 → 6` and drifts HSL saturation by ±6 across the
ramp. HSL lightness is not a perceptual quantity, and constant HSL saturation is not
constant chroma. Measured consequence: the maximum attainable chroma in sRGB at a fixed
OKLab lightness varies by **2.7× across hue at L = 0.85** (0.0736 at h = 270 vs 0.2018 at
h = 120) and by **7.2× at L = 0.95**. A ramp that ignores this produces yellows that read
washed out and blues that read muddy at the same nominal saturation. Full table in
`appendix/gamut-table.md`.
→ `theme/T2-color-engine.md`

### F-02 · The shade map is recomputed on every theme render — `lib/colorPaletteParser.ts:47`
`generateInlineStyleObject` calls `generateShadeMap(color, 22)` once per accent (4 accents),
during render, uncached. Each call performs 22 HSL→RGB conversions plus a 22-element
nearest-color search, and 22 HSL→hex conversions. It is invoked from:
`ThemeApplier.tsx:18` (wraps the entire app), `ThemeMakerSidebar.tsx:18` (every editor
render), and `ConfigFavicon.tsx:104` (every favicon). `ToastDisplayLegacy.tsx:19` runs a
separate 24-step map. None of it needs to exist: `highlight-*` and `darklight-*` are simply
other rungs of the same ladder.
→ `theme/T4-compiler.md`

### F-03 · Ten precompiled gradient strings per theme — `lib/colorPaletteParser.ts:168-176`
`generateWidgetGradients` emits `--bg-widget-10 … --bg-widget-100`: the same gradient
serialized ten times with different alpha multipliers, so that `bg-widget-70` can exist.
Cost is 10× the CSS and 10× the compile work, and the set of available opacities is fixed
at ten. One gradient plus one `--surface-alpha` custom property replaces all of it.
→ `theme/T5-surfaces-and-gradients.md`

### F-04 · Every widget renders an identical gradient — `tailwind.config.ts:92-106`
`bg-widget-*` sets `background-image` with `background-size: cover; background-position:
center`. A 40 px button and a 900 px card therefore display the *same relative slice* of
the same gradient. This is the "same shape" defect: the site's widgets look like scaled
copies of one another. It is structural, not cosmetic.
→ `theme/T5-surfaces-and-gradients.md §4`

### F-05 · `ColorGradient` is an intersection of partials — `interfaces/theme.ts:163-172`
```ts
type ColorGradient = { type; stops?; disabled?; colorInterpolation? }
  & Partial<LinearGradientData> & Partial<LinearGradientOrientationData>
  & Partial<RadialGradientData> & Partial<CircleRadialGradientAdditionalData>
  & Partial<CustomGradientData>;
```
Every gradient carries every field of every gradient kind. Nothing is type-checked:
`posX` on a linear gradient is legal. `lib/themeMaker/layerHelper.ts:104-120`
(`initializeGradientDataProperties`) exists to backfill the fields the type cannot
guarantee, and `lib/themeMaker/profileOptimizeTool.ts:60-140` exists to strip the ones that
do not apply. Both disappear under a discriminated union.
→ `theme/T3-schema.md §3`

### F-06 · CSS is generated by a string template mini-language — `lib/colorPaletteParser.ts:6-17, 107-127`
Gradient syntax is expressed as
`"[{isCircle ?? false} | circle | null] [{isCircle ?? false} | {sizeKeyword ?? farthest-corner} | {sizeX}% {sizeY}%] at {posX}% {posY}%"`
and evaluated with two chained regexes and a `evaluateGradientRuleValue` coercion helper.
This is an interpreter for a language with no grammar, no errors, and no tests. A
discriminated union plus one `switch` is shorter and total.
→ `theme/T4-compiler.md §3`

### F-07 · `siteThemeColor` is a sibling of the palette but is an accent — `interfaces/theme.ts:100-108` vs `:203`
`ThemeDataConfig.siteThemeColor` sits outside `palette`, yet `AccentColors` includes
`"site"`, so every consumer special-cases it: `SettingsContext.tsx:169`
(`updateSiteThemeColor`), `faviconHelper.tsx:39-41`, `colorHelper.ts:12-26` (two index maps
that both carry a `site` entry). It is a palette role.
→ `theme/T3-schema.md §2`

### F-08 · `isWidgetOpacity` is a compiler concern stored on data — `interfaces/theme.ts:120-125`
A gradient *stop* declares whether it participates in surface opacity. That is a property of
the surface material, not of a color stop. The `custom` gradient kind goes further and
stores a raw CSS string containing the literal token `$opacity`, string-replaced at
`colorPaletteParser.ts:164-166`.
→ `theme/T5-surfaces-and-gradients.md §3`

### F-09 · A theme is defined in four places
Adding one theme requires edits to `interfaces/theme.ts` (`ThemeKey` union, 55 members),
`components/theme/util/themeKeyMap.ts` (import + map entry), and
`components/theme/util/listedThemesMap.ts` (display order). Backdrops additionally require
`ThemeAnimatedBackgroundKey` (36 members) and `backgroundAnimationMap.tsx`. The lists are
already out of sync: `oasis`, `lollipop`, `cubistic`, `springField`, `defaultEditor`, and
`birthdayGeneric` are theme configs absent from `allListedThemes`, and `themeKeyMap.custom`
points at `oasisConfig`.
→ `theme/T3-schema.md §6`

### F-10 · `generatePenumbraConfig` proves the thesis and shows the cost — `components/theme/config/penumbra.ts`
This file already does what the whole engine should do: take `{hue, saturation, brightness}`
multipliers and generate a theme. It is 260 lines because `transformRgb` must be applied to
each of ~40 literal RGB triplets by hand, it operates in HSL, and it carries a hard-coded
special case for one shadow color (`SHADOW_RGB`, line 8). `lib/constants/defaultSettings.ts`
calls it 11 times to synthesize the entire dark-mode theme set.
→ `theme/T2-color-engine.md`, `theme/T9-theme-migration.md`

### F-11 · The corpus is already ramp-shaped — measured
Of 58 parseable theme configs, **57 have monotonic OKLab lightness** across
`primary → saturated → pastel → light`; 31 are dark-scheme, 27 light-scheme; hue torsion
across the four roles has median 11.8° and p90 35.5° (measured over the 37 fully chromatic themes). The existing themes *are* tone ladders
with per-role deviations. The engine in `theme/T2` is not an imposition on this corpus; it
is a description of it. Reproduced by `node appendix/corpus.mjs`.

### F-12 · A flat relative-chroma envelope fits the corpus; a tapered one does not — measured
Three candidate chroma envelopes were fitted against all 58 themes. Residual `|Δ relative
chroma|` after fitting a per-theme seed chroma:

| envelope | p50 | p90 | max |
| --- | --- | --- | --- |
| flat (`relC = chroma`) | **0.147** | 0.349 | 0.490 |
| gentle taper | 0.194 | 0.422 | 0.477 |
| strong taper | 0.485 | 0.650 | 0.651 |

The gamut ceiling `Cmax(L, h)` already supplies the perceptually correct taper; adding a
second envelope on top of it fights the corpus. Default envelope is therefore **flat**.
→ `theme/T2-color-engine.md §4`

## 3. Animated backdrops

### F-13 · Three backdrops are one shader with different constants
`whiteout/WhiteoutAnimatedBackground.tsx`, `velvet/VelvetAnimatedBackground.tsx`, and
`planetoid/PlanetoidAnimatedBackground.tsx` contain byte-identical `NOISE_GLSL` blocks

| file | `baseColor` | `highlightColor` |
| --- | --- | --- |
| whiteout | `vec3(0.954, 0.961, 0.993)` | `vec3(0.792, 0.807, 0.89)` |

| planetoid | `vec3(0.11, 0.129, 0.09)` | `vec3(0.149, 0.29, 0)` |

→ `theme/T6-backdrops.md`

### F-14 · Backdrop color is hard-coded, so backdrops are not reusable
No backdrop reads the theme palette. Every one embeds its palette as literals, in GLSL, CSS
modules, or SVG assets. Reusing `velvet`'s field under a green theme is impossible without
editing the shader. This is the reusability problem the charter names as O4.
→ `theme/T6-backdrops.md §3`

### F-15 · No backdrop accepts configuration
`backgroundAnimationMap.tsx` maps a key to a *pre-instantiated element*
(`photos: <PhotosAnimatedBackground />`). There is no props channel, so there is nothing to
configure and nothing for the editor to expose.
→ `theme/T6-backdrops.md §2`

### F-16 · Five independent WebGL contexts
`gallery3D`, `gold`, `planetoid`, `velvet`, `whiteout` each mount `<Canvas>`. A theme with a
multi-key `animatedBackgroundKey` array mounts several simultaneously. Browsers cap
concurrent WebGL contexts (typically 8–16) and each costs memory and a compositor layer.
→ `theme/T6-backdrops.md §5`

### F-17 · Each backdrop re-reads `settings.backgroundRichness` itself
36 call sites duplicate the quality decision, each interpreting the three tiers
differently, and each subscribing to the settings context to do so.
→ `theme/T6-backdrops.md §4`

### F-18 · `prefers-reduced-motion` is never consulted
Zero occurrences in the repository. 36 animated backdrops, window mount animations, toast
choreography, and image-viewer transitions all ignore it.
→ `ux/U3-motion-a11y.md`

## 4. Document format and content

### F-19 · The component syntax is a regex split — `lib/markdownParser.tsx:94, 133`
```ts
const blocks = input.split(/(&&\{\w+\}\{.+?\}&&)/g);
const props = JSON.parse(`{${propsString}}`);
```
Consequences: props must be JSON without outer braces and without `}` anywhere inside;
`.+?` is single-line so no multi-line props; no nesting; no escaping, so the literal `&&{`
cannot appear in prose; a malformed block silently renders the string
`Error rendering component X` (`:81-85`).
→ `data/D2-document-format.md`

### F-20 · Every markdown block becomes `dangerouslySetInnerHTML` — `lib/markdownParser.tsx:148-155`
Each non-component block is wrapped in its own `<div dangerouslySetInnerHTML>`. So a
document is a sequence of sibling divs rather than a document, which is why the CSS in
`lib/reading-markdown.module.css` has to re-establish spacing per block, and why headings
cannot be React components.

### F-21 · `marked`'s global renderer is mutated per call — `lib/markdownParser.tsx:129, 198, 220, 245`
`marked.use({ renderer })` mutates module-global state. Four separate functions
(`parseCustomMarkdown`, `generateTOCSectionData`, `needTOC`, `findTopLevelHeader`) install
different renderers and never restore. Any interleaving — two windows rendering two
articles, or a TOC computed during a parse — yields the wrong renderer. `needTOC` parses the
document twice (`findTopLevelHeader`, then itself) and `generateTOCSectionData` parses it a
third time.

### F-22 · Components are stripped with a second, different regex — `lib/markdownParser.tsx:161, 207` and `lib/blog/helper.ts:28`
Three regexes attempt to remove component blocks so TOC generation and reading-time
estimation can ignore them, and they do not agree:
`/&&\{.+\}\{.+\}&&/g` (greedy, so it eats everything between the first and last block on a
line) vs `/&&[^&&]*&&|&&[^&&]*\n/g`.

### F-23 · Three component registries — `lib/markdownParser.tsx:31`, `lib/serverOnlyMarkdownComponentsMap.tsx`, `lib/clientWindowMarkdownComponentsMap.tsx`
`commonComponentsMap` also imports six theme-editor components, so importing the markdown
parser pulls the theme editor into the bundle.

### F-24 · Two inline grammars, one of them inverted — `lib/lightMarkUpProcessor.tsx:303`
```ts
const inlineRegex = /\\(.)|\*(.*?)\*|_(.*?)_|`(.*?)`|\|(.*?)\|/g;
```
`*x*` renders `<em>`, `_x_` renders `<strong>`. Markdown means the opposite. `|x|` means
mark. `~~{text}{url}~~` is a link and `@@{text}{email}@@` is a mailto, while `@@keyword@@`
in the *document* grammar means an inline SVG glyph — the same sigil, two meanings, two
parsers. `restoreDisplayText` (`:118`) then attempts to invert all of it with six more
regexes for use in `<meta>` descriptions.
→ `data/D2-document-format.md §5`

### F-25 · Parallel arrays that must stay length-aligned — `interfaces/entry.ts:8-13`
```ts
interface ImagesData { url: string[]; text?: string[]; aspectRatio: string; original?: string[] }
```
One `aspectRatio` string for all images, parsed with `.split(":").map(Number)` at eight sites.
`ImageViewer.tsx:18-47` (`imageViewerTextParser`) exists solely to pad/truncate `text` and
`original` back into alignment. Real intrinsic dimensions per image are unavailable, so
`next/image` is given `Math.min(2500, …)` guesses (`ImageViewer.tsx:693-700`).
→ `data/D1-content-model.md §3`

### F-26 · `unlisted` is read but not declared
`(entry as any).unlisted` at `app/photos/page.tsx:38`, `app/blog/feed.rss/route.ts:22`,
plus casts in both `[slug]/layout.tsx` files. Absent from `PostData`, `PhotosEntry`,
`ProjectsEntry`.

### F-27 · Comments have no identity — `interfaces/comment.ts`
`CommentEntry` has no `id`. Deletion targets an array **index** and guards it by comparing
`author`/`content`/`date` (`app/api/comments/deleteSingleComment/route.ts:44-50`). Under
concurrent writes the index is wrong and the guard produces "please refresh the page". Same
for replies (`deleteReply/route.ts:51-61`).
→ `data/D1-content-model.md §5`, `data/D4-storage-and-concurrency.md`

### F-28 · Three date representations
`dayjs` + two plugins (`lib/dateUtil.ts`), `date-fns` (`components/widgets/Timeline.tsx:1`,
parsing `"yyyy-M-d"`), and raw `new Date(a) > new Date(b)` sorting
(`awsEntryFetcher.ts:147-152`). Two libraries shipped for what `Intl` does natively.

## 5. API and storage

### F-29 · Verbs in paths, camelCase segments, no versioning
`/api/accountState/login`, `/api/comments/addComment`, `/api/comments/deleteSingleComment`,
`/api/comments/likeSingleComment`, `/api/entry/readEntryBySlug`, `/api/themeMaker/analyzeImage`.

### F-30 · The client supplies storage paths — `lib/dataLayer/client/clientEntryReader.ts:15-22`
The browser sends `directory=blog/text&mode=markdown&fields=…`, i.e. the S3 layout and the
serialization format are part of the public wire contract. The server then defends with an

### F-31 · Every failure is HTTP 500 with an internal message
18 of the 21 handlers use `try { … } catch (error: any) { return new Response(JSON.stringify({
error: error.message }), { status: 500 }) }`. Missing parameter → 500. Not logged in → 500.
Banned → 500. Comment too long → 500. And `error.message` is returned verbatim to the
client.
→ `data/D3-api.md §5`

### F-32 · Read-modify-write with no concurrency control — `lib/dataLayer/server/commentManager.ts:37-105`
`getComments` → mutate → `uploadCommentsToServer`. Two overlapping comment posts: the
second `PutObject` overwrites the first. The same pattern governs entry likes, user
settings, and the Christmas tree. This is the risk the charter acknowledges — and S3
conditional writes (`If-Match` on `PutObject`) resolve it without a database.
→ `data/D4-storage-and-concurrency.md`

### F-33 · Four S3 clients, four copies of credential validation
`accountStateManager.ts:40`, `awsEntryFetcher.ts:38`, `commentManager.ts:27`,
`specialServiceManager.ts:22` each construct `new S3Client` and each re-throw on missing
env vars at module scope. Four gunzip-stream pipelines are also duplicated verbatim.

### F-34 · Cache policy is ad hoc
`revalidate` values of 24, 25, 30, 3600, 0, and `24` (as "hours"?) appear across routes;
`readAllEntries` sets `s-maxage=1800`; `getComments` sets `no-store`;
`banOrUnbanUser` calls `revalidatePath("/")`. Next 16 provides `cacheLife`/`cacheTag` and
`revalidateTag`.
→ `data/D3-api.md §6`

## 6. State and rendering

### F-35 · One monolithic settings object consumed by 115 files — `components/contexts/SettingsContext.tsx`
`SettingsState` has 41 fields including 16 full theme profiles (`customThemeData`), the
window layout, and the notebook contents. It is exposed as a single context value, so any
change to any field re-renders every one of the 115 consuming subtrees. This is the single
largest performance defect in the codebase.
→ `data/D5-state-and-settings.md`, `perf/P1-rendering-architecture.md`

### F-36 · Synchronous `JSON.stringify` of everything on every update — `SettingsContext.tsx:112`
Inside the `setSettings` updater. Triggered by window drag end, window resize, window
activation, every color-picker frame, every gradient-stop scrub. The payload includes all
16 theme profiles.

### F-37 · Settings state is mutated in place — `SettingsContext.tsx:152-155, 163-166`
```ts
const themeData = [...settings.customThemeData];   // shallow
themeData[settings.customThemeIndex].palette[entry] = content;   // mutates the live object
```
The shallow copy does not protect the profile object. Previous state is mutated, so
`_.isEqual` guards elsewhere compare an object with itself.

### F-38 · `setState` called from inside `useMemo` — `GradientDataContext.tsx:92, 188`, `FaviconEditorContext.tsx:86`
Index clamping is implemented as a memo that calls a setter. Clamping needs no state at all.

### F-39 · Four nested `setState` updaters used as a state read — `WindowContext.tsx:476-479`
`saveWindows` nests `setWindows(→ setWindowStates(→ setWindowOrder(→ setWindowSaveProps(…))))`
purely to read four pieces of current state, then writes the result into a *fifth* state
(`windowSaveDataBuffer`) which an effect (`:617`) drains into `updateSettings`.

### F-40 · Six positionally-indexed parallel arrays — `WindowContext.tsx:75-86`
`windows`, `windowStates`, `windowOrder`, `windowRefs`, `windowCleanupData`,
`windowSaveProps`. Every mutation must update all six consistently; `removeWindowByPredicate`
(`:221-271`) re-maps order values by hand and each of the six setters carries a
`if (prev.length < prevWindows.length) return prev` desync guard.

### F-41 · Both responsive branches mount before hydration — `components/widgets/MobileDesktopEntryRenderer.tsx:27-36`
Initial state `0` renders **both** `mobile` and `desktop` children, then an effect narrows.
`MainPageEffect.tsx:201` uses it for `<WindowManager />`, so the whole window system mounts
on mobile for one commit.

### F-42 · Polling on timers — `CommentCardContainer.tsx:34` (10 s), `EntryLikeButton.tsx:77` (5 s), `ChristmasTreeDisplay.tsx:17` (8 s)
Unconditional `setInterval`; no `visibilityState` gate; each tick is an uncached S3 GET
through a route handler.

## 7. Window engine

### F-43 · Pointer state in React state, applied imperatively anyway — `WindowInstance.tsx:456-461, 1148-1156`
`handleResizeMove`/`handleDragMove` call `setWindowState` on every pointer move. Because
`windowStates` is one array in a shared context, *every* window re-renders on *any*
window's drag. An effect at `:1148` then writes `style.width/height/left/top` directly —
so the React state round-trip is pure overhead.

### F-44 · Manual touch-identifier bookkeeping — `WindowInstance.tsx:167-182, 505-520`
Separate `mouse*`/`touch*` paths with `Array.from(e.touches).find(t => t.identifier === …)`
fallbacks. `lib/helperHooks.ts:331-419` (`useDragAndTouch`) exists to manage the
window-level listeners and carries a `dependencies: any[]` escape hatch for the stale
closures this creates. Pointer Events with `setPointerCapture` removes all of it.

### F-45 · Modifier keys observed via four window listeners per window — `WindowInstance.tsx:1175-1193`
`keydown`/`keyup` × `handleResizeMove`/`handleDragMove`, re-registered whenever
`windowState`, `windowDraggingData`, `windowResizingData`, `isWindowDragging`, or
`isWindowResizing` changes — i.e. on every pointer move. Modifier state is already on the
pointer event.

### F-46 · Snapping does O(n²) forced layout — `WindowInstance.tsx:688-1146`
`snapToClosestWindow` calls `getBoundingClientRect()` on every window, and
`isUnobstructed` calls `window.getComputedStyle(...).zIndex` inside a loop over all windows,
itself called inside a loop over candidate sides inside a loop over windows. Every
geometry value it needs is already in `windowStates`, and z-order is already `windowOrder`.
`initiateWindowCleanup` (`WindowContext.tsx:327-427`) has the same shape.

### F-47 · Window *data* contains React elements — `interfaces/window.ts:2`
`WindowData.content: React.ReactNode`. Because instance data is also the persisted shape,
`WindowSaveData` must `Omit` the un-serializable fields, and `requireAllDataSaved` /
`specificDataKeyToBeSaved` exist to choose which of the remaining 23 fields to persist
(`WindowContext.tsx:498-521`). Restoration then `cloneElement`s a shared element
(`:563-567`). Separating definition from instance deletes this entire mechanism.

### F-48 · The window registry statically imports every widget — `components/window/WindowPickerEntry.tsx:43-297`
`windowEntryMap` is a module-level object containing JSX for 16 widgets: the blog reader
(and therefore the markdown pipeline), the management reader, the calculator, the signal
generator, the three.js favicon, the settings panel, and two iframes. Anything importing
`useWindow` transitively pulls all of it.

## 7a. Overlay (popup) layer

484 lines across `PopUpContext` (105), `PopUpActionContext` (34), `PopUpManager` (67),
`PopUpDisplay` (91), `DarkOverlay` (46), `ExpandedImagePopUp` (134). Twelve call sites. It is the
**modal peer of the window system** — built at the same time, same idioms, same defects — and it
sits between windows and notifications in the stacking order.

### F-70 · Two stacking systems with hardcoded, uncoordinated z-index tiers
`WindowManager.tsx:14` puts all windows at `z-[11]`; `PopUpDisplay.tsx:59` puts every popup at
`z-50` with its utility button at `z-70`; `DarkOverlay.tsx:40` is also `z-50`;
`ToastBannerReceiver.tsx:15,25` is `z-80`; `NavbarWrapper.tsx:55,61` is `z-30`; the side menu is
`z-20`. Six tiers, all literals, in six files, with no single place that says what the order is —
so "should a popup cover the navbar" is answered by grep.
→ `perf/P2-windowing.md §10`

### F-71 · Overlay stacking is by array index, like windows before F-40
`popUps: PopUp[]`; `PopUpDisplay` receives `index` and compares `index === popUps.length - 1` to
decide whether it is the active one (`:44`, `:66`). `removeAllPopUpsFrom(index)` slices by
position. Same class of defect as the window engine's six parallel arrays.
→ `perf/P2-windowing.md §10`

### F-72 · `DarkOverlay` fights the DOM with a `MutationObserver` — `DarkOverlay.tsx:13-35`
It sets `document.body.style.overflow = "hidden"`, then installs a `MutationObserver` on
`document.body` that re-asserts it whenever *anything* changes body style. Two stacked overlays
therefore each observe and each re-assert, and on unmount each clears `overflow` unconditionally —
so closing the inner of two nested popups restores scrolling while the outer is still open.
`MenuSlideWrapper` also writes `document.body.style.overflow` (`:31-37`), which is precisely the
mutation the observer exists to undo.
→ `perf/P2-windowing.md §10`

### F-73 · Popup ids are minted with the toast prefix — `PopUpContext.tsx:44`
```ts
uniqueId: _.uniqueId("toast_"),
```
Harmless today because nothing parses the prefix; a copy-paste that shows the two systems were
written from the same template. `appendPopUp` is otherwise correct (it uses the updater form,
unlike `appendToast`, F-54).

### F-74 · No focus management on any overlay
`PopUpDisplay` renders content into a `fixed` div with no `role`, no `aria-modal`, no focus trap,
no focus restoration, and no `inert` on the page behind. `PopUpManager.tsx:23-41` handles `Escape`
with a window-level `keydown` listener re-registered on every `popUps` change. The `<dialog>`
element provides all of it.
→ `ux/U3-motion-a11y.md §3.2`, `perf/P2-windowing.md §10`

## 8. Image viewer — `components/widgets/ImageViewer.tsx` (787 lines)

### F-49 · Leaked `wheel` listener — `:419-425`
```ts
const clearPageWindow = () => { if (!hasScrollingHitBoundary) clearTimeout(timeoutId); };
imageContainerRef.current?.addEventListener("wheel", clearPageWindow);
```
Added inside the `wheel` handler; never removed. One additional permanent listener per wheel
event, each capturing a stale `timeoutId` and `hasScrollingHitBoundary`.

### F-50 · The `wheel` handler is re-attached every render — `:588-622`
`handleScroll` and `handleDoubleClick` are re-created each render and appear in the effect's
dependency array, so the listeners are removed and re-added on every render.

### F-51 · Seventeen `useState` hooks driving one carousel — `:70-94`
Including `containerTransition` (a CSS string), `horizontalTranslation`, and five
gesture-bookkeeping values. All of it is what `scroll-snap-type: x mandatory` does natively.

### F-52 · Grid view fights React — `:285-387`
`enableGridView`/`turnOffGridView` iterate `container.childNodes`, assign `node.style.*`
including `zIndex`, force reflow with `container.offsetHeight;` (`:316`, commented as a
"browser hack"), and orchestrate state through nested `transitionend` listeners.

### F-53 · Every image is `priority` — `:701`
With `images.unoptimized: true` in `next.config.ts`, every image in every viewer is
preloaded at `fetchpriority=high`, at full original resolution. An album page renders one
viewer per entry.

## 9. Notifications

### F-54 · `appendToast` drops toasts — `ToastContext.tsx:53`
`setToast([...toast, processedToast])` reads `toast` from the render closure instead of using
the updater form. Two `appendToast` calls in one tick: the second overwrites the first.
`removeGivenToast` (`:72`) has the same defect.

### F-55 · The queue is drained by effect feedback — `ToastCardColumnManager.tsx:26-36`
An effect depending on `[toasts, activeToasts, slotLimit, removeToast]` calls
`removeToast(0)` and `setActiveToasts`, which re-triggers itself. `deactivateToast` (`:38`)
mixes a stale `activeToasts` closure with a `toastsRef` mutable read.

### F-56 · Two complete notification renderers
`ToastDisplayLegacy.tsx` (80 lines, own color maths, own timers) and the
`ToastBannerReceiver` → `ToastCardColumnManager` → `ToastCardColumnMember` →
`ToastCardSwiper` → `ToastCard` chain (5 components, 464 lines), selected by
`settings.notificationStyle`. `ToastBannerReceiver` duplicates its layout twice for
mobile/desktop through `MobileDesktopEntryRenderer`.

### F-57 · Enter/exit animated via `max-height` — `ToastCardColumnMember.tsx:15,31,57-58`
`maxHeight` transitioned from `0px` to `scrollHeight`px, with dismissal driven by an
`onTransitionEnd` on the same element (which also fires for descendant transitions). A
`toastMounted` flag is threaded down to `ToastCardSwiper` to sequence the two animations.
`@starting-style` plus `transition-behavior: allow-discrete` replaces the whole mechanism.

## 10. Theme editor — `app/design/theme-maker/` (121 files)

### F-58 · Every editor gesture writes global settings
`updateAccentColor`, `updateGradientData`, `updateFaviconConfig`, `updateThemeMisc` all call
`updateSettings`, which stringifies 41 fields to `localStorage` and re-renders 115
subtrees. `doSync` gates only the *network* call, not the local write. A color-picker drag
does this at pointer-event rate.

### F-59 · `structuredClone` per property change
`GradientDataContext.updateGradientProperty` (`:110`) clones the selected layer *and* the
entire layer array on every change; `modifyGradientStop`, `deleteGradientStop`,
`appendGradientStop`, `updateGradientStopsDirectly` each clone twice more. 63 call sites
repo-wide.

### F-60 · The color-preview sidebar recompiles the theme on every render — `ThemeMakerSidebar.tsx:18`
`generateInlineStyleObject(currentCustomThemeConfig.palette)` — four 22-step shade maps plus
ten gradient serializations — with no memo.

### F-61 · Editor UI is delivered through the markdown pipeline
`lib/markdownParser.tsx:40-45` registers `themeAccent`, `themeGradient`, `themeProfile`,
`themeFavicon`, `themeMisc`, `themeSidebar` so that S3-hosted markdown can embed the theme
editor. `app/design/theme-maker/page.tsx` is `export default function ThemeMakerPage() {}`
and the real UI is in `layout.tsx`. **Seven** route `page.tsx` files are empty functions;
`03-hygiene.md §5` enumerates all seven and owns the fix.

## 11. Styling and build

### F-62 · 149 `@apply` directives across 48 CSS Modules
Tailwind v4 requires `@reference` in each module for `@apply` to resolve theme-dependent
utilities, which re-parses the referenced stylesheet per module and degrades IntelliSense.
The occurrences are, however, overwhelmingly trivial — `@apply gap-4` (8×),
`@apply pointer-events-none select-none` (7×), `@apply hidden` (4×). Only ~12 reference
theme colors. Elimination is cheaper than accommodation.
→ `perf/P5-tailwind-v4.md §4`

### F-63 · `postcss-each` is a dependency with zero uses
`grep -rn "@each" --include="*.css" .` → no matches. `autoprefixer` also becomes redundant
under v4.

### F-64 · `shadow-xs` already means something custom — `tailwind.config.ts:48`
The v3 config defines `boxShadow.xs`. Tailwind v4 renames v3's `shadow-sm` → `shadow-xs`.
The 5 existing `shadow-xs` usages will silently change meaning on migration.

### F-65 · The color system is built on the `<alpha-value>` channel-triplet hack — `tailwind.config.ts:23-41`
`primary: "rgb(var(--color-primary) / <alpha-value>)"` requires colors to be stored as
space-separated channel triplets, which is why `ColorTriplet` exists, why `color-convert` is
a runtime dependency, and why 88 `bg-opacity-*` utilities are used instead of `/alpha`. In
v4, `@theme inline` plus `color-mix()` makes all of it unnecessary.

### F-66 · Types are global ambient declarations — `interfaces/**` (17 files)
No file imports or exports. `HexColor`, `ColorTriplet`, `WindowData`, `SettingsState`, and
~90 other names are globally in scope everywhere. No module graph, no rename safety, no
per-domain ownership, and `tsconfig.json` `include` picks the directory up twice through
overlapping globs.

### F-67 · Route directories hold 121 non-route components
`app/design/theme-maker/` contains 121 files, of which 2 are routes. `app/blog/`,
`app/photos/`, `app/projects/`, `app/christmas-tree/` are similar.

### F-68 · `images.unoptimized: true` — `next.config.ts:26`
Comment: `// turning this on for now since limit reached`. Every image is served at full
original size. Combined with F-53 this is the largest byte-weight item on the site.

### F-69 · A prebuild script rewrites source files in place — `prebuild-helper/svg-id-randomizer.js`
`predev` mutates `.tsx` files under `components/assets`, prepending the string literal
`"id random";` as a sentinel. Source files are build artifacts. Runs only on `predev`, never
on `build`, so dev and prod can diverge.
